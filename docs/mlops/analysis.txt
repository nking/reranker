Hugging Face has Qwen/Qwen2.5-0.5B-Instruct
    - is small SOTA pretriained LLM with instruction task training
    - Training Stage: Pretraining & Post-training
    - is capable of being futher trained for tasks:
        - SFT with a prompt that includes a user query, candidate movies and enriched
          information about both.
    - the LLM uses full softmax self-attention in all 24 layers, giving it 4x as many all-to-all
       cross-item comparison layers for short (~250-token) ranking prompts
   - it uses standard matrix-multiplication attention so should work well on CPU and T4x2 GPUs
   - more resilient to the diversity of system prompts
   - Long-context Support up to 128K tokens and can generate up to 8K tokens.
   - Multilingual support
   - Context Length: Full 32,768 tokens and generation 8192 tokens
   the rest of the model card: https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct

HuggingFace trl is chosen
   - robust APIs
   - lots of documentation
   - actively maintained and updated
   - SFTrainer

Data Pre-processing:
    - training:
      - the inputs are read in from parquet and formatted into a prompt for the LLM
      - datasets API from HuggingFace wrapping data in an Arrow Table
    - inference
      - the online inputs are given and formatted into a prompt, ready
        to be sent to the LLM over gRPC

    SFTTrainer (via Hugging Face Trainer and accelerate) automatically handles DistributedSampler for training
    and distributed shard-and-gather for evaluation
    when the script is launched with torchrun or accelerate launch.
    SFTTrainer automatically falls back to standard RandomSampler / SequentialSampler
    when run on a single GPU or CPU.

Training:
    - CPU and GPU able and data parallel capable
       - single-process and multi-GPU Distributed Data Parallel (DDP) in SFTTrainer needs:
          - DDP-Safe Parquet Loading & Prompt Formatting
            - when loading parquet dataset, need to use with state.main_process_first():
               to prevent read contention race conditions for multi-GPU processes.
            - both trainingand inference need to use the same render_prompt_and_completion
              method to avoid data shift.
            - DDP wrapper safegauards for call model embedding projector layer
              with self.accelerator.unwrap_model(self.model) and using
              self.accelerator.is_main_process for ONNX/checkpoint file writes.
    - will use a SFTTrainer to be a listwise contrastive learning
      trainer that uses composite_ndcg_k for HPO selection
      and early stopping metric.
        - Single CPU / Single GPU (python train_reranker.py):
          PartialState().num_processes == 1.
          Trainer.get_train_dataloader() uses standard RandomSampler(train_dataset).
          Trainer.get_eval_dataloader() uses standard SequentialSampler(eval_dataset).
        - Multi-GPU DDP (torchrun --nproc_per_node=2 train_reranker.py):
          PartialState().num_processes == 2 and PartialState().process_index is 0 or 1.
          Trainer.get_train_dataloader() automatically wraps the dataloader
              in accelerate's distributed BatchSamplerShard
              (equivalent to DistributedSampler(shuffle=True, seed=args.seed))
              and automatically calls set_epoch(epoch) at the start of every epoch.
          Trainer.get_eval_dataloader() shards eval_dataset across GPUs,
          runs prediction_step in parallel, and all_gathers the candidate logit
          predictions back into their exact original dataset order before calling
          compute_metrics function—so eval_qrels_dict ("q_0", "q_1", ...)
          remains aligned without any changes needed.
    - will use optuna for HPO


Export:
    - because the listwise SFTing of the pretrained Qwen LLM 
      doesn't generate text auto-regressively, and instead 
      executes one forward pass then extracts the log-probabilities 
      of the TOP_K candidate tokens at final position,
      no K-V cache is needed.
      Therefore the entire computation can be fused into a single
      execution graph and that means we can use a C++ static graph.
      - ONNX supports quantization and works well on CPU, GPU and 
        mobile.
        - Triton (onnxruntime_onnx C++ backend) or Rust ort gRPC
        - ONNX Runtime Mobile (ort Rust crate or C++/Swift/Kotlin)
      - docker compose compatible for local testing
      - compatible w/ <...> for high quality production serving

Inference:
   - the ranker project has the rust end-to-end inference
     and it will be extended to make calls to this
     trained model

Prompt Formatter:
   - Training / Eval: Reads pre-processed rows from Parquet
     (query_time, history_items, candidate_items, labels, ranked_labels, user_embedding,
     candidate_embeddings, ranker_embs),
     optionally subsamples top_k candidates if the Parquet file stored a larger candidate pool
     (e.g., 20 candidates), and formats them into "prompt", "completion", and "ranker_embs".
     The storing more candidates than needed and sub-sampling from them helps keep a randomly
     selected negatives list for training.
   - Inference: Receives the pre-processed dictionary inline in-memory from
     RerankerPreprocessor.preprocess_inference_batch(...) and formats "prompt" and "ranker_embs"
     directly without touching disk.
