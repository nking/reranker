Because we freeze the 4-bit NF4 base weights of Qwen2.5-0.5B-Instruct
and only train 2,185,088 parameters across q_proj, k_proj, v_proj, o_proj, gate_proj,
up_proj, down_proj plus the RankerEmbeddingProjector, we do not have
catastrophic forgetting of the pretrained base model representations.

Additional size reduction techniques, these are from the Song Han MIT Lab:
   - Cross stage distillation
      - happens during ListwiseSFTTrainer.compute_loss (KL-div against candidate_scores which are already in Parquet)
      - adds a temperature scaled KL divergence term between the ranker soft distribution
        p_ranker=softmax(s_ranker/temp) and the LLM's 5-candidate distribution
        p_LLM=softmax(z_LLM/temp).
        adds essentially nothing to the training and inference runtime executions.
        - acts as label smoothing that is grounded in the ranker embedding geometry.
   - SmoothQuant (W8A8) / AWQ (W4A16)
      - happens after training, after merge_and_unload() but before export_to_triton_onnx.
      - directly accelerates the serving binary
      - the Tesla T4 has 65 TFLOPS of FP16 Tensor Core compute
        and 130 TOPS of INT8 Tensor Core compute (2 x higher than FP16).
        SmoothQuant places scales s intot he eqn Y = X * Diag(s)^-1 * Diag(s) * W so that
        the weights and activations run in INT8.
      - AWQ finds the 1% most salient weight channels by their activation strengths
        on validation prompts and then quantizes them to INT4.
        the FP16 model size of ~1GB is reduced to ~350MB.
      - there is a 15-30 sec increase on eval_dataset expected durign training
      - the inference latency should be 2.5 - 2 times lower
      - the inference VRAM should be ~60% lower even when keeping ranking_emb_projector and lm_head in FP16

Export:
    - because the listwise SFTing of the pretrained Qwen LLM 
      doesn't generate text auto-regressively, and instead 
      executes one forward pass then extracts the log-probabilities 
      of the TOP_K candidate tokens at final position,
      no K-V cache is needed.
      Therefore the entire computation can be fused into a single
      execution graph and that means we can use a C++ static graph.
      - ONNX supports quantization and works well on CPU, GPU and 
        mobile.
        - Triton (onnxruntime_onnx C++ backend) or Rust ort gRPC
        - ONNX Runtime Mobile (ort Rust crate or C++/Swift/Kotlin)
      - docker compose compatible for local testing
      - compatible w/ <...> for high quality production serving
    - we want to save the final trained model much in the way that the orbax best
      checkpoint is saved for the ranker project and can later be exported to different
      formats.  we also need the file to not be very large because downloading large
      files from Kaggle can be difficult.
    - we can save only the trained deltas
      (lora_adapter/ + ranker_projector.safetensors + reranker_config.json + tokenizer + a tiny 32-sample calibration file
      for SmoothQuant/AWQ)
      to create a self-contained ~10 MB portable checkpoint that can later be converted
      to any ONNX quantization format locally.
    - here is a list of exports
       - the portable checkpoint created by save_portable_reranker_checkpoint (~12 MB)
         - stores lora_adapter / (r=16), ranker_projector.safetensors (88 KB),
         reranker_config.json, tokenizer.json, calibration_inputs.npz
       - Merged SafeTensors created by safetensors_dir (~2GB)
         - Full merged Qwen2.5-0.5B weights + ranker_projector.safetensors
       - Triton ONNX — FP32 created by quantize_mode="none" (~2GB)
         - Unquantized OnnxExportableQwenReranker (1/model.onnx)
       - Triton ONNX — SmoothQuant W8A8 (created with quantize_mode="smoothquant_w8a8") (~ 500MB)
         - SmoothQuant outlier migration ($\alpha=0.5$) + INT8 dynamic quantization
       - Triton ONNX — AWQ W4A16 (created with quantize_mode="awq_w4a16") (~ 315MB)
         - AWQ salient-channel grid search + 4-bit group-128 quantization
         - is the minimum VRAM and disk footprint

      - that means that the same query with different candidates can be made and the results

Prompt Formatter:
   - Training / Eval: Reads pre-processed rows from Parquet
     (query_time, history_items, candidate_items, labels, ranked_labels, user_embedding,
     candidate_embeddings, ranker_embs),
     optionally subsamples top_k candidates if the Parquet file stored a larger candidate pool
     (e.g., 20 candidates), and formats them into "prompt", "completion", and "ranker_embs".
     The storing more candidates than needed and sub-sampling from them helps keep a randomly
     selected negatives list for training.
   - Inference: Receives the pre-processed dictionary inline in-memory from
     RerankerPreprocessor.preprocess_inference_batch(...) and formats "prompt" and "ranker_embs"
     directly without touching disk.

Misc details
-------------------

how the ranker embeddings are handled in the SFT model:
 (1) the prompts in the datasets have placeholders "<|vision_pad|>" for each embedding.
 (2) when the prompt is tokenized in step 1 of model.forward
     self.tokenizer.encode("<|vision_pad|>")
     maps each occurrence to a single integer token ID (self.emb_token_id = 151654
 (3) at train time, method _init_projector_and_hook creates a trainable nn.Linear(embedding_lnegth, 896)
     layer (hidden_size = 896 for Qwen2.5-0.5B) and attaches it directly as an attribute
     on the unwrapped Qwen model.
     Right before calling model(**inputs), compute_loss pops ranker_embs (batch_size, 6, 24)
     from inputs (so Qwen2ForCausalLM.forward does not reject an unexpected keyword argument)
     and stashes self._current_ranker_embs and self._current_input_ids on self.
     - Intercepting embed_tokens in _inject_ranker_embs_hook:
        When model(**inputs) runs, the very first operation inside Qwen2 is embed_tokens(input_ids),
        which outputs output of shape (batch_size, seq_len, 896). ****
        PyTorch immediately invokes _inject_ranker_embs_hook(module, hook_inputs, output)
        before the first Transformer layer executes:
           - projects the ranker embeddings
           - makes a mask for the embedding placeholder locations
           - clones the output and overwrites the embedding placeholds with the embeddings
           - then the Qwen model layers 0 through 24 see them.
           - in inference, the injection steps are handled in OnnxExportableQwenReranker.forward

       │
       ▼ (Contains "ranker_embs": shape [6, 24])
[Custom Data Collator] ──(Pops & collates into batch["ranker_embs"])
       │
       ▼

       ▼

       │
